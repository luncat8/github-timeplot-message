# 0.1.0 - GitHub Timeplot Message - Dev Plan

## Goal
Single-file vanilla JS app (no build) that lets user paint a 7x53 grid like GitHub contributions graph.
Painted image maps to real commit counts over time to produce message/picture in GitHub profile.

## Draft Requirements (parsed)
- same style plot as on github
- input line for text or draw rectangles with pointer
- slider to move date related to image horizontally, by set week
- buttons fill, clear
- draw tools: draw, erase
- slider to adjust draw amount
- amount is relative and draw color related to max amount
  - example: 0,1 -> 0,255 ; 0,2,3 -> 0, 255/4*3, 255
  - typically green on white bg similar to github theme
- auto save, load at start localStorage. import, export. compact efficient save format
- get user commits to sync with image plan and suggest todays commit number related to yesterday (high and low levels to print image)
- if text add option subpixel smooth font - to not only use low and high commit numbers but also some other for grayscale antialiasing

## Non-goals / Constraints
- no build, no npm, single index.html + maybe one js/css file, ES module if needed
- no legacy browsers, modern evergreen only
- no backend, all local + GitHub public API
- AGENTS.md style: tab indent, no alloc in hot path, flat logic

## UX Layout Proposal

```
[Header: title | github username input | sync btn | import export]
[Main: canvas grid + tooltip]
[Controls row 1: Text: [input text_______] [font: 5x7 pixel select] [subpixel ☑] [Render Text btn] ]
[Controls row 2: Tools: (Draw) (Erase) (Rect) | Amount: [slider 1-10] [value] | Fill Clear | Grid lines toggle]
[Controls row 3: Time offset: [slider weeks 0-52] label: start date -> end date | Today suggestion box]
[Footer: legend for colors, commit mapping: Low [__] High [__] -> today needs X commits]
```

- Canvas: shows 53 cols x 7 rows, plus month labels top, day labels left (Mon Wed Fri) like GitHub.
- Cell size ~16px + gap 3px => canvas ~ 1000x150. Responsive scaling via devicePixelRatio.
- Hover shows date + level + required commits.
- Pointer: mouse/touch draw.

## Data Model

- Grid: `W=53`, `H=7`, total 371. Could allow variable width but fixed 53 simplifies date math.
- Storage: `Uint8Array(371)` levels 0..maxLevel (maxLevel configurable, default 4). 0 = empty.
- `maxLevel` derived from data: `max = Math.max(...data)`. If 0 then 0.
- `offsetWeeks`: int, 0 = image ends today (or starts 53 weeks ago). Positive moves start forward? Define:
  - `endDate = today` (or last Saturday)
  - `startDate = endDate - 53*7 days + offsetWeeks*7`
  - Slider: -52 .. +52? Simpler 0..52 meaning how many weeks from start of year window. Default 0.
  - Better: slider represents start week index within 53. Image always 53 wide but we can scroll underlying timeline? Simplest: slider shifts where in the 53-week window the painted data sits, or shifts real calendar dates. Spec: "slider to move date related to image horizontally, by set week." So implement offset of image relative to calendar.
  - So grid dates = for each col, row: compute absolute date from offset.

- Color mapping:
  - Normalize: `t = level / max` if max>0 else 0. If max==1 then 0,1 => 0,1.
  - GitHub palette (light theme):
    - 0: #ebedf0 (or #f0f0f0)
    - 1: #9be9a8
    - 2: #40c463
    - 3: #30a14e
    - 4: #216e39
  - For arbitrary max: interpolate or quantize to 5 levels for preview, but keep continuous alpha for canvas green intensity.
  - Proposed: keep 2 modes:
    - quantized: `q = round(t*4)` -> palette[q]
    - continuous: `green = lerp(light, dark, t)` using same hues.
  - For spec example: they want relative amount. So implement continuous: `rgba(0, 100+ t*155, 0)` or use GitHub green scale. Simpler: use `level/max * 255` for opacity over base green.
  - Amount slider: sets current paint level 1..10 (or 1..maxLevel). User can increase max by painting higher than current max, auto grows max.

## Interaction

- Tools:
  - draw: on pointerdown/move, set cell to current amount
  - erase: set to 0
  - rect: drag start->end, fill rect with amount on pointerup (preview during drag)
- Fill: fill all with current amount
- Clear: set all 0
- Text input:
  - User types string, we rasterize to grid using bitmap font.
  - Need built-in 5x7 or 3x5 pixel font for clean block letters. Could also use canvas text measure then downsample.
  - Flow: type -> click Render -> overwrites grid centered.
  - Subpixel smooth option: when checked, use anti-aliased font rendering via offscreen canvas 4x scale then downsample averaging to produce intermediate levels 0..4 for grayscale. If unchecked, threshold to 0/1 (or 0/max).
  - Implementation for subpixel:
    - Create offscreen canvas width = W*cellScale, height = H*cellScale, scale factor e.g., 4.
    - Draw text with `ctx.font = 'bold Xpx monospace'` centered.
    - Get ImageData, for each grid cell compute average alpha (0-255), map to level = round(alpha/255 * maxLevel)
  - For pixel font: have simple table `font5x7` A-Z,0-9, etc. Render with spacing 1 col.

- Amount slider: range 0..10, but 0 means erase? Better 1..10. Display value. On change, update brush.

- Date slider:
  - `<input type=range min=0 max=52>`
  - On input, recompute startDate, re-render month labels, update suggestion.

## Storage

- Auto save: on any data change, debounce 300ms -> localStorage setItem `gtm-v1` JSON.
- Load at start: try localStorage, else empty.
- Compact format for import/export:
  - Need efficient: not JSON array of 371 ints verbose but ok. Compact: base64 of Uint8Array + metadata.
  - Proposal format v1: `GTM1:<max>:<offset>:<base64>` where base64 encodes Uint8 packed 4 bits per cell if max<=15 else 8 bits.
  - For simplicity first implement: JSON `{v:1,w:53,h:7,max:4,off:0,data:"<base64>"}` then stringify and for export provide both: compact string and JSON file download.
  - Base64: use `btoa(String.fromCharCode(...bytes))` but for large safe.
  - Also support plain text export: rows of numbers e.g., "0 1 0 ..."
  - Import: accept either format, try parse.
  - UI: buttons Export (copies to clipboard + downloads .gtm.txt), Import (prompt + file input).

- Goal: user wants to know how many commits to do today to achieve image.
- Inputs: GitHub username, Low commits (e.g., 1), High commits (e.g., 10)
- Fetch contributions:

  - Option B: GraphQL contributionsCollection (needs token for private, but public works with unauth? Actually needs auth). Could use unofficial API: `https://github-contributions-api.deno.dev/{user}.json` or `https://github.com/users/{user}/contributions` parsing? Best use `https://api.github.com/graphql` with optional token input.
  - Simpler MVP: use `https://github-contributions-api.deno.dev/{username}.json` - returns array of {date, count}. CORS allowed. Fallback to scraping `https://github.com/{user}`? That page has data in DOM but CORS block.
  - So implement fetcher abstraction with two providers:
    - primary: `https://github-contributions-api.deno.dev/{user}.json`
    - secondary: `https://api.github.com/users/{user}/events` approximate
  - Cache in localStorage.

- Sync logic:
  - After fetch, we have map date->actual commits last year.
  - We have planned grid date->level.
  - Compute: for each date in grid that is in past, compare actual vs expected? Or just visualize overlay? For MVP, overlay actual as border or second layer? But spec: "get user commits to sync with image plan and suggest todays commit number related to yesterday (high and low levels to print image)."
  - Suggest today's commits:
    - Need yesterday's actual commit count? Or yesterday's planned level?
    - Interpretation: If yesterday you did high level (e.g., 10 commits) and today your image wants low level (1 commit), suggestion relative to yesterday? Or suggest based on low/high mapping?
    - Proposed formula:
      - User defines `lowCommits` and `highCommits` (e.g., low=1, high=10)
      - `maxLevel` from image (e.g., 4)
      - For any level L, required commits = `low + (high-low) * (L/max)`
      - For today: get `todayLevel` from grid at today's date (computed via offset). Suggest `requiredCommitsToday`.
      - Also show yesterday's actual vs expected to adjust: e.g., if yesterday you did fewer than expected, maybe today still same? But spec says "related to yesterday (high and low levels to print image)" - maybe they want to detect high/low from yesterday's actual to calibrate? Simpler: show yesterday actual and today suggested, with note "yesterday you did X (level Y), today needs Z".
    - UI box: "Today (2026-09-21) planned level 3/4 => do 8 commits (range 1-10). Yesterday you did 2 commits (actual)."

## Rendering Pipeline

- No per-frame loop. Render on demand via `requestAnimationFrame` batched.
- Function `render()`:
  - clear canvas, account DPR
  - draw background white
  - draw month labels: iterate cols, if first day of month, draw text
  - draw day labels left
  - for each cell (col,row):
    - compute date
    - compute level = data[col*7+row] (or row-major? Need decide column-major as GitHub: week col, day row. Index = col*7+row)
    - t = level/max
    - color = palette quant or continuous
    - if date is future -> dimmed? GitHub doesn't show future, but we can gray out.
    - if date == today -> stroke highlight
    - fill rect with gap
  - if overlay actual contributions available: draw small dot or border if actual>0
  - draw rect preview if dragging

- Performance: reuse canvas, no allocations in render loop besides maybe.

## Open Questions / Decisions Needed

- Date alignment: GitHub contributions start on Sunday. Should we align? Yes, start week on Sunday to match GitHub.
- Max level auto-grow: if user paints level 10 while max was 4, max becomes 10. Should we cap at 10? Slider max 10 reasonable (GitHub has 4 levels but user may want more granularity for subpixel).
- Rect tool: should it be separate tool or modifier (Shift+drag)? Proposal separate tool button.
- Text font: pixel vs system font? Provide both: if subpixel off -> pixel font, if on -> system bold monospace with antialias.
- Save format final decision: start with JSON+base64 for compactness, ~500 chars for whole image.
- GitHub API rate limit: deno API is unofficial but ok for MVP. Document fallback and need for token later.

## Risks & Mitigations

- GitHub API CORS / rate limit -> use multiple providers, cache, show error message, allow manual low/high without fetch.
- Canvas text antialias differs per browser -> test Chrome/Firefox, use willReadFrequently.
- LocalStorage quota (5MB) -> our data <1KB, fine.
- Pointer events outside canvas while dragging -> use setPointerCapture.
- Mobile touch -> same pointer events, increase cell hit area.
